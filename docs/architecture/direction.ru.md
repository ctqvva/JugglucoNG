**Статус:** действующий план. Раздел 1 фиксирует решения мейнтейнера и внутри PR по задаче не пересматривается; всё остальное — рекомендации, их можно оспорить в PR, объяснив почему.
**Дата:** 2026-09-23. **Замерено на:** `main` @ `5f7edd924` (1.2.1) и открытом стеке #373–#397.
**Для кого:** контрибьюторы и агенты, с которыми они работают. Перед любой структурной задачей прочитайте §1, §3 и §8.
**Английская версия:** [`direction.md`](direction.md). Версии держатся синхронными; при расхождении прав английский файл, а само расхождение — баг.

Этот документ — продолжение первого раунда PR по рефакторингу (T0.0–T0.3, T5.1, T2.1–T2.3). Те PR писались по более раннему предложению, которое в репозиторий так и не попало. Два более поздних черновика тоже жили только вне репозитория. Этот файл заменяет все три как единая точка отсчёта: сохраняет то, в чём они сходились, фиксирует решения, которые мейнтейнер теперь принял, и меняет курс там, где первый раунд показал путь лучше.

Правила проекта, которые действовали и до этого документа и продолжают действовать:

- **Выборочные мержи из upstream продолжаются** для ещё не заменённых частей legacy-базы. Лучше рефакторить файлы, от которых мы уже ушли; не создавать лишних правок в файлах, которые ещё сверяются с upstream Juggluco.
- **Никогда не прекращать публикацию показаний глюкозы** и не показывать сенсор истёкшим на основании догадок драйвера. Любое изменение, которое может придержать показание, требует явного «да» от мейнтейнера.
- **Обработка сигнала в драйверах, временные метки и сетки сенсоров** — зона подписи мейнтейнера, без исключений.

2. **Добавить `assembleWearRelease`** (достаточно arm64) в задание сборки. T5.1 переносит классы в `src/main`, и они впервые попадают под R8 в приложении часов. Сейчас минифицированный APK часов не собирает никто.

### 2.2 Первая партия T5.1 (#376–#384) — принять, дальше сменить рецепт

Первая партия сократила число двойников с 36 до 25 и добавила `NoDuplicateFqnTest`, чей allow-list может только сокращаться. Изменения сохраняют поведение:

- `Applic.isWearable` — константа времени компиляции, поэтому ветки только для часов исчезают из байткода телефона.
- Слияние `AlarmActionReceiver` отправляет пользовательские алерты через `CustomAlertAccess`. Телефон регистрирует движок в `Applic.onCreate`, поэтому действие из уведомления, которое поднимает процесс с нуля, всё равно до него доходит.

**Чего этот рецепт не даёт.** «Перенести класс телефона в `main` и добавить `if (isWearable) return;`» устраняет расхождение двух копий — это главный выигрыш. Но часы по-прежнему молча ничего не делают: пустышка просто переехала в ветку `if`. Для функций из первой партии это приемлемо, потому что у часов их и не должно было быть: экран батареи, broadcast-ы LibreLink, Gadgetbridge и виджет на рабочем столе. Для функций из D1 это **неприемлемо**, и это не тот инструмент, когда классу нужны ресурсы или библиотеки, которые есть только у телефона. В §4 — рецепт на каждую категорию.

**Стек.** Одиннадцать PR по одной паре, где каждый показывает дифф всего стека, отнимают больше времени на ревью, чем стоят сами изменения. Дальше — см. §8.1.

### 2.3 Гейт метрик T0.3 (#386) — переделать до мержа

Скрипт работает, но жёстко падает на 15 grep-счётчиках, включая `runcatching_swallowed`, `kotlin_object_singletons`, `volatile_fields`, `root_package_files` и `root_package_loc`. На открытом PR мейнтейнера с исправлением #371 (выбор сенсора на часах при двух сенсорах) он падает на четырёх из них. Последний означает, что любая строка, добавленная где угодно в корневой пакет `tk.glucodata`, краснит CI. Предсказуемый итог: каждый PR поднимает baseline, и гейт перестаёт что-либо значить.

Как переделать:

- **Жёсткий гейт** (правильное направление никогда не вызывает сомнений):
  - файлы с Composable, которые зовут `Natives.`
  - файлы с Composable, которые зовут `Applic.`
  - файлы с Composable, которые напрямую трогают `SharedPreferences`
  - поиски `Class.forName` из `src/main` в код телефона или часов
  - вхождения `fallbackToDestructiveMigration`, зафиксированные на 0
  - двойники уже покрыты `NoDuplicateFqnTest`; здесь их не считать, чтобы не проверять одно и то же дважды
- **Только отчёт** (печатается в логе CI вместе с динамикой и никогда не валит сборку): всё остальное — `@Volatile`, `runCatching`, `Thread(`, `Handler(`, число `object`, строки по пакетам, файлы длиннее 2000 строк.
- JUnit-тест, сканирующий исходники в стиле `ProguardKeepRulesTests`, лучше JUnit-теста, который запускает `bash`. Если shell-скрипт остаётся для локального использования, тест не должен от него зависеть.
- Baseline брать с `main` в момент мержа, а не с ветки.

### 2.4 SettingsStore T2.1–T2.3 (#387–#397) — на паузе, затем перенаправлен

Код аккуратный. В проверенных областях типы хранимых значений, значения по умолчанию и семантика `apply()` совпадают со старым кодом. И проблема с настройками, которую трек взялся решать, тоже реальная. Трек поставлен на паузу, потому что он взялся не за те файлы и не включил ту часть, которая устраняет баги.

**Что на самом деле лежит в prefs-файлах.** Их 24, и в них перемешаны четыре вида данных, которые требуют разного обращения:

| Вид | Примеры | Где им место |
|---|---|---|
| Пользовательские настройки | параметры прогноза и сглаживания, единицы, цвета, настройки Nightscout и outbound API, свои звуки | реестр настроек, описанный ниже |
| Состояние сенсоров и секреты | ключи сопряжения AiDex, AES-ключи iCan, параметры калибровки MQ по сенсорам и курсоры пакетов | собственные записи сенсора (§6, Q5); никогда не экспортируются и не зеркалируются на часы |
| Рабочее состояние | сроки «отложить», последняя попытка / последняя ошибка, история ошибок BLE, закрытые баннеры, телеметрия | рядом с компонентом-владельцем |
| Кеши | `wear_journal_cache`, кешированные метаданные обновления | где удобно |

Большинство из 9 перенесённых областей — рабочее состояние, а не настройки: «отложить», история ошибок BLE, закрытые подсказки готовности, учёт бэкапов и обновлений, запросы маршрутизации часов. Настоящее расползание не тронуто. `tk.glucodata_preferences` открывается из 79 мест, где имя файла написано строкой, плюс в 41 файле объявлена собственная константа с тем же именем, и ни один ключ не объявлен в одном месте.

**Баг с настройками, у которого есть доказательства: значения по умолчанию заданы в нескольких местах.** `WearPrefsSync` зеркалирует на часы 10 настроек телефона по списку, который ведётся вручную и повторяет тип и значение по умолчанию для каждого ключа. Его собственный комментарий фиксирует сбой: переключатель прогнозной симуляции показывал «выкл» на часах, когда на телефоне был «вкл», потому что часы откатывались к другому значению по умолчанию. Сегодня значение по умолчанию горизонта прогноза (120) объявлено отдельно в четырёх файлах, а скорости всасывания углеводов (35 г/ч) — в пяти. Сейчас они совпадают; ничто не следит, чтобы так и оставалось. Функции часов из D1 добавляют новые настройки, которые часам нужны с телефона: типы и чувствительность инсулина, URL и секрет Nightscout. Каждая стала бы ещё одной строкой, добавленной в список вручную.

**Чего фасад не исправляет.** Живые обновления — не проблема: дашборд перечитывает настройки на каждое событие `UiRefreshBus`. Это грубо, но работает. `observe()` не чинит ничего, что сейчас сломано.

**Что строить вместо этого: реестр настроек.** Каждая *пользовательская настройка* объявляется один раз, и каждое чтение идёт через это объявление. Объявление указывает:

- файл, ключ, тип и значение по умолчанию
- **область**: только телефон, только часы, или принадлежит телефону и зеркалируется на часы
- **политику бэкапа/экспорта**: включать, не включать, или секрет
- допустимый диапазон, где он есть (`GlucoseDelta.sanitizeIntervalMinutes` — сегодняшняя ручная версия)

Список `WearPrefsSync` тогда генерируется из объявлений с областью «зеркалируется», и значение по умолчанию у ключа не может расходиться само с собой. `SettingKey(file, name, default)` из #388 — правильная основа; ему не хватает политик.

**Пилот:** 10 настроек прогноза и сглаживания, которые `WearPrefsSync` уже зеркалирует. Их мало, они уже ездят на часы, и перенос убирает класс багов, который действительно случался. После этого настройки, стоящие за функциями часов из D1, объявляются как «зеркалируется» с первого дня. Экспорт/импорт настроек потом почти даром получается из флага бэкапа; строить ли его — открытый вопрос O5.

**Два риска, которые пилот обязан учесть:**

1. **Объединение значения по умолчанию может изменить поведение.** Для каждого ключа *до* переноса выписать все места чтения и их значения по умолчанию. Где два читателя расходятся, какое значение победит, решает мейнтейнер. Это продуктовое решение, и его никогда не сглаживают внутри рефакторинга.
2. **На старой установке ключ может быть сохранён с другим типом.** Типизированное чтение откатывается к значению по умолчанию и один раз пишет в лог. Исключение не бросается.

**Исправления, которые взять из поставленного на паузу кода:**

- Сверять сохранённое значение с объявленным типом ключа вместо `as? T` при стёртом параметре типа — оно выпускает несовпадение наружу как `ClassCastException` в месте вызова.
- Читать через типизированные геттеры, а не через `SharedPreferences.getAll()`, который копирует весь файл при каждом чтении. На маленьких файлах это безвредно, а на основном prefs-файле, который и важен, дорого.
- Один экземпляр хранилища на процесс, регистрируемый при старте, как остальные мосты (P1).
- In-memory бэкенд и контрактный тест оставить — оба хороши.

**Вне рамок:**

- Настройки, которые хранятся в нативном хранилище и доступны через `Natives` (D3).
- Состояние сенсоров и секреты (Q5).
- Рабочее состояние. Чистые выделения вроде `SnoozeStore` приветствуются, когда область трогают по другой причине, вместе с их тестами, прямо поверх `SharedPreferences`. Это не работа с настройками, и реестр для них не нужен.

Реестр — не отдельный трек. Он относится к Q2 и Q3 (§6), потому что зеркалирование настроек — часть протокола телефон↔часы, а функциям часов оно нужно. Из #387–#397 сохранить `SettingKey`, in-memory бэкенд, контрактный тест и тесты по областям. Переносы областей — отбросить.

## 3. Архитектурные принципы

Это идеи, на которых держится каждый рецепт ниже. Если ситуация не подходит ни под один рецепт — возвращайтесь к ним.

**P1. Общий код не называет код варианта.** `src/main` не должен обращаться к классам телефона или часов по имени — ни через одноимённый класс в каждом source set, ни через `Class.forName`. Вместо этого `src/main` объявляет интерфейс, а каждый вариант регистрирует свою реализацию в `Application.onCreate`. Рабочий пример — `CustomAlertAccess` / `TrendAccess`, регистрируемые из `Specific.registerBridges()`. Регистрация именно в `onCreate` важна: `Specific.start()` выполняется слишком поздно для boot-ресиверов и перезапущенных сервисов.

**P2. «На часах нет» — объявленный факт, а не молчаливая пустышка.** Возможности, которой у варианта нет, просто нет в реестре. Вызывающий код это видит и сам решает, что делать: спрятать кнопку, один раз записать в лог или вернуть типизированный результат. Метод, который на одном из вариантов возвращает `null` или ничего не делает, — ровно тот паттерн, ради устранения которого всё это затеяно.

**P3. Общим делаем домен, а не legacy-UI.** Большинство оставшихся двойников — экраны на View из эпохи upstream: `IOB.mkview`, `Nightscout.show`, `Meal.menuview`. Когда функция нужна часам (D1), общим становится логика за контрактом (расчёт IOB, отправщик в Nightscout, записи в журнал). У часов свой UI на Compose. Legacy-экран на View остаётся только на телефоне и никогда не портируется.

**P4. У каждого вида данных один владелец.** У каждого вида данных (текущее показание, история, журнал, калибровка, метаданные сенсора, настройка) ровно один авторитетный писатель. Все остальные компоненты читают или сверяют. Новый код, который пишет те же данные из второго места, возможен, только если это прописано в документе о владении хранилищами (§6, Q5).

**P5. Рефакторинг и изменение поведения никогда не в одном PR.** Структурный PR пишет в описании «поведение не меняется» и как это проверено. Если рефакторинг вскрыл баг, исправление идёт отдельным PR — до или после.

**P6. Выделяем из работающего кода.** Абстракцию вводим, когда у неё уже есть или вот-вот появятся два реальных пользователя. Никаких фасадов «на вырост», универсальных хранилищ и фреймворков.

**P7. Поведение на реальном устройстве важнее элегантности.** Для BLE, хранилища и алгоритмов сенсоров зелёные unit-тесты необходимы, но недостаточны. PR сообщает, что проверено на железе, или прямо говорит, что не проверено ничего.

**P8. Сначала фиксируем то, что есть.** Характеризационные тесты пишем до переноса кода. Фейки лучше моков, реального времени в тестах не бывает, имена тестов — предложениями. Регрессионный тест называет коммит или issue, от повторения которого он защищает.

**Без DI-фреймворка.** Ручной регистрации и внедрения через конструктор хватает на всё в этом плане. Встраивание Hilt, Koin или Dagger в статический мир `Applic` — отдельный проект, в рамки этого плана не входит. (Это предлагаемая норма, а не одно из решений §1. Если не согласны — поднимите вопрос с мейнтейнером.)

## 5. Следующий трек: обвязка для тестов миграций Room

### Почему это и почему сейчас

Миграции Room — единственное место, где баг навсегда уничтожает историю пользователя, и сейчас их не проверяет ничто:

- `HistoryDatabase` — **версия 32**, 21 объект `Migration`, `exportSchema = false`. `CalibrationDatabase` — **версия 5**, тоже с `exportSchema = false`. Схема в JSON не закоммичена нигде.
- `HistoryDatabaseSafetyTests` проверяет, что в исходнике нет определённой строки. Это гигиена исходников, а не тест миграций.
- `CloneRecoveryMigrationTests` читает сгенерированный Room код из `build/generated/ksp/...`, что хрупко по самой конструкции. T0.0 уже пришлось его перенаправлять.
- Выпущенные версии `HistoryDatabase`: **1.0.3–1.1.2 → v11**, **1.1.3 → v12**, **1.2.0 и 1.2.1 → v32**. Скачок с 12 на 32 частично произошёл в интеграционных ветках. Комментарий в классе записывает: «main v19, a Clone build at v20–v23, a test build at v24–v31». Номера версий фактически принадлежали веткам — именно так две сборки получают один и тот же номер для разных схем.
- Выпущенные версии `CalibrationDatabase`: до 1.1.2 включительно → v3, 1.1.3 и позже → v5.

### Шаги

**H1. Экспорт схем.** Поставить `exportSchema = true` в обеих базах и передать KSP `room.schemaLocation` с путём `Common/schemas/`. Закоммитить `32.json` и `5.json` калибровок. Добавить шаг CI, который падает, если сборка изменила файлы в `Common/schemas/`, а они не закоммичены (`git diff --exit-code Common/schemas`).

**H2. Восстановить схемы выпущенных версий.** Разовая археология в отдельной копии репозитория. Для каждого выпущенного тега (`1.1.2-Alpha` для v11, `1.1.3-Alpha` для v12, и соответствующие для калибровок) локально включить экспорт схемы, один раз запустить KSP и забрать JSON. Закоммитить как `11.json`, `12.json` и так далее. Сами теги не меняются; коммитится только JSON.

**H3. Средство запуска тестов миграций.** Предпочтительный вариант — Robolectric плюс `MigrationTestHelper` из `androidx.room:room-testing`: это стандартный инструмент, и он сверяет результат с экспортированным JSON. В проекте Room 2.8.4. Robolectric пока не подключён; подключить его — часть трека. Начать с однодневного спайка. Если Robolectric здесь не заведётся, запасной вариант — тонкий адаптер `SupportSQLiteDatabase` поверх драйвера `sqlite-jdbc`, который тесты уже используют: он применяет настоящие объекты `Migration` и сравнивает результат с JSON.

**H4. Тесты.**

- Для каждой выпущенной версии N (11, 12, 32; калибровки 3 и 5): создать базу версии N с характерными строками — история нескольких сенсоров, записи журнала, надгробия удалённых показаний, калибровка. Промигрировать до текущей версии. Сверить схему с JSON и проверить, что строки сохранились с ожидаемыми значениями.
- Тест, что `fallbackToDestructiveMigration` не используется. Он уже существует как проверка исходника — оставить.
- Переписать `CloneRecoveryMigrationTests` на новое средство запуска, чтобы он больше не читал `build/generated`.

**H5. Правило с этого момента.** Повышение версии схемы попадает в `main` первым, отдельным PR, с новым JSON и тестом миграции. Интеграционные ветки (`test/*`) никогда не вводят версию схемы; чтобы её получить, они перебазируются на `main`.

**Готово, когда:** PR, который повышает версию без миграции, падает; PR, чья миграция удаляет колонку или теряет строки, падает; `CloneRecoveryMigrationTests` проходит на чистой копии без предварительной сборки.

**Ревью мейнтейнера:** весь трек целиком. Он затрагивает семантику хранения (§8.3).

## 6. После обвязки — очередь

По одному треку, в этом порядке, если мейнтейнер не решит иначе. Каждый пункт — трек с пилотным PR.

**Q1. Регистрация вместо рефлексии.** Сейчас в `src/main` около 20 вызовов `Class.forName`, которые ведут примерно к 16 классам: `HistoryRepository`, `HistorySync`, `CalibrationManager`, `GlucoseUncertaintyStore`, классы доступа к журналу, `OutboundApiJournalSnapshot` (его ищут в трёх местах), `JournalTreatmentUploader`, `NightscoutJournalFollowerImporter`, `NotificationPredictionOverlay`, `AlarmActivity`, `ComposeHostKt` и два класса доступа к восстановлению клона. Каждому нужно keep-правило ProGuard, иначе он ломается только в минифицированных сборках — такое уже случалось. Заменить каждый интерфейсом в `src/main` и регистрацией в `Specific.registerBridges()`, затем удалить его keep-правило и запись в `ProguardKeepRulesTests`. Двойники категорий P и R из §4 идут тем же треком — механизм у них тот же. Счётчик: `Class.forName` из `src/main` — примерно с 20 до 0. Динамический поиск в `Log.java` мостом не является, его не считать.

**Q2. Типизированный протокол телефон↔часы.** В `MessageSender` было 28 строковых путей; теперь это `WearMessagePath`, который `MessageReceiver` разбирает в `when`, проверяемом компилятором на полноту, и охраняет `WearMessagePathManifestTests` (#490, затем #494 для убранного `/settings`). Про версию: **структурированные нагрузки несут свою, а версию протокола держит рукопожатие** -- строка `v:` через `WearProtocol.accepts` для текстовых нагрузок, байт версии у `WearSync2`/`WearJournalSync`/`SensorOwnershipRuntime`, `"version"` в JSON передачи сенсора. Поле в каждом сообщении способно только повторить версию, которую рукопожатие уже объявило, и стоило бы бампа протокола на каждом устройстве. **Две командные нагрузки -- исключение, которое это подтверждает:** `/sync2/calcmd` открывается байтом команды, а `/displayprefs/mainsensor` -- токеном действия, поэтому не знающий значения сосед уже логирует его и игнорирует, а расширяется нагрузка новой командой или новым действием, то есть ровно тем же, чем дал бы байт версии, только без поломки. Новые часы со старым телефоном иначе потеряли бы переключатели калибровки, а APK обновляются по отдельности, так что это реальное окно. Если нагрузке всё же понадобится версия поверх её тега, версия -- это `WearProtocol.VERSION`, и отправитель спрашивает `WearProtocol.peerVersion()`, прежде чем слать новую форму. Всё, что несёт форму, версию несёт. Не несут: две командные нагрузки выше, которые различимы своим же тегом; `/start` и `/netinfo`, чей формат -- нативная C-структура, и версия у них появится, когда структура изменится; и семейство однобайтовых -- `/bluetooth`, `/messages`, `/sensorclaimstatus`, `/toggles/req`, `/displayprefs/req`, `/defaults`, `/askforstart`, `/wake`, `/wakestream` -- плюс `/calibrate`, где лежит один int в mg/dL. Один байт версионировать нечего: значение, которого получатель не знает, отвергается как неизвестное, и исход тот же, что при несовпадении версий. (`/data` -- это зеркало телефон-телефон, и по этому же разделу оно остаётся на собственной обвязке.) «Старые часы / новый телефон» и «новые часы / старый телефон» остаются обязательными тестами. В дизайн стоит заложить два урока из недавней работы в поле:
- Сторона должна понимать, что говорит с несовместимой сборкой. Debug-пакет телефона и release-пакет часов вообще не могут обмениваться сообщениями, и сейчас этот сбой проходит молча.
- Данные, привязанные к сенсору, должны нести идентификатор сенсора. Сейчас, если id сенсора нет, калибровка откатывается к «самой свежей ревизии», и второй сенсор получает чужую калибровку.

`SensorOwnershipRuntime` уже и есть машина состояний передачи сенсора — типизировать её сообщения, а не переписывать её. Протокол клона/зеркала между телефонами пока остаётся отдельным; общий конверт не навязывать.

Реестр настроек из §2.4 приходит в этом треке. Начинается он с пилота — 10 настроек, которые `WearPrefsSync` уже зеркалирует. Типизированное сообщение с настройками тогда генерируется из реестра, а не из второго списка, который ведётся вручную.

**Q3. Функции часов из D1** (IOB/COB, самостоятельный Nightscout, записи журнала/еды) поверх Q2, по рецепту категории W из §4. Это PR с новыми функциями и ревью как для изменения поведения, а не рефакторинг. Каждая настройка, которая нужна этим функциям на часах, объявляется в реестре настроек с областью «зеркалируется» с первого же PR. Секреты вроде API-секрета Nightscout помечаются как секрет: они передаются, только если мейнтейнер согласен, что часы могут их хранить.

**Q4. Двойники категории S**, в конце — `Specific`. Allow-list **закрывается на трёх записях по решению, а не становится пустым**: `Meal` относится к Q3, а `ui.AlarmActivity` и `tk.glucodata.Specific` остаются намеренно — первый потому, что его имя класса закреплено манифестами, второй потому, что `src/main` не может назвать класс из `src/mobile` или `src/wear`, так что одноимённый bootstrap для каждого варианта — это механизм, а не недосмотр (решение в #475).

**Q5. Документ о владении хранилищами.** Один владелец на каждый вид данных. Для каждого записать: идентичность, авторитетного писателя, что считается дубликатом, порядок, обработку отката часов, сверку и удаление. Писать по сегодняшнему коду: `HistoryRepository` и `CalibrationManager` владеют Room; нативное mmap-хранилище владеет сенсорами Libre/Dexcom и прочими с нативным хранением; между ними стоят `VirtualGlucoseSensorBridge` / `VirtualSensorNativeMirror`; восстановление клона — четвёртый писатель. Он также охватывает состояние драйверов и учётные данные по сенсорам, которые сейчас лежат в prefs-файлах (ключи сопряжения AiDex, AES-ключи iCan, параметры калибровки MQ), — реестр настроек их намеренно не включает. Этот документ — условие для любого контракта хранилища. **Первая версия написана: [`storage-ownership.md`](storage-ownership.md).** Таблицы владения и учётных данных в ней сверены с кодом; порядок, откат часов, сверка и удаление записаны как открытые вопросы, потому что выдуманный ответ хуже открытого. ## 8. Рабочие правила

Файл с инструкциями для агентов в репозиторий не входит, поэтому правила, важные для этой работы, записаны здесь.

### 8.1 Треки, стеки и размер PR

- **Одновременно один открытый структурный трек** (D4). Трек начинается от `main`, никогда не от другого открытого трека. Глубина стека — не больше трёх.
- **Пилот, потом партии.** Первый PR рецепта маленький, его читают целиком. Следующие PR применяют тот же рецепт к 5–10 элементам каждый, ссылаются на пилот и называются по имени рецепта.
- **В описании каждого PR:** какой рецепт он применяет; «поведение не меняется» (или какое изменение поведения он вносит); что запускалось (unit-тесты телефона и часов, какие сборки); что проверено на устройстве — или «на устройстве не проверялось».
- **Не открывать PR по задаче, которую план поставил на паузу.** Сначала спросить.

### 8.2 Сборка и тесты перед push

- Всегда: `./gradlew :Common:testMobileDebugUnitTest :Common:testWearDebugUnitTest`.
- После любой правки в `src/main` или в нативном коде — ещё `./gradlew :Common:assembleWearDebug`. У часов своя конфигурация CMake, поэтому сборка телефона про них ничего не доказывает.
- Всё, что переносит код между source set-ами или трогает рефлексию и keep-правила, — ещё release-сборка обоих флейворов.
- Перед завершением — `git diff --check`.
- Изменения логики в драйверах, алертах или нативной политике получают отдельные unit-тесты в `Common/src/test/` (или в `testMobile/`, `testWear/`, если они специфичны для флейвора).

### 8.3 Всегда полное ревью мейнтейнера, независимо от рецепта

- обработка сигнала в драйверах, временные метки, сетки сенсоров, математика калибровки
- пороги алертов, доставка алертов, поведение «отложить» и тихого окна
- схемы и миграции Room; семантика нативного хранилища; всё, что может потерять или придержать показание
- владение сенсором и его передача между телефоном и часами

### 8.4 Гейты

- Allow-list или счётчик может только уменьшаться. Понижение потолка — часть того PR, который его заработал.
- Новый *жёсткий* гейт в CI — только с согласия мейнтейнера. Гейт, который краснит обычные исправления, обходится дороже, чем долг, который он отслеживает (§2.3).

### 8.5 Прочее

- Новые строки интерфейса идут в `values/strings.xml` **и во все локали `values-*`** — с переводом, а не на английском.
- Цифры из этого документа перепроверяйте, когда берёте задачу: по мере мержей они меняются. Если цифра здесь неверна — исправьте её в том же PR.
- Никаких трейлеров `Co-Authored-By` для ИИ-инструментов в коммитах.

## 9. Ответы на handoff по T5.1

В handoff для #373–#384 было четыре вопроса.

1. **Какой вариант — A, B или C?** Ни один в чистом виде. Двойники сейчас ставим на паузу, как в C, потому что первой идёт обвязка Room. Но на 11/36 насовсем не останавливаемся и не возвращаемся ни к переносу по одной паре (A), ни к построению общего механизма заранее (B). Оставшиеся пары закрываются по категориям, каждая внутри того трека, к которому относится её рецепт: P и R — с регистрацией (Q1), W — как функции поверх типизированного протокола (Q2–Q3), S — последними (Q4). Реестр экранов телефона из §4 — узкий, заработанный вариант B. Рецепты по каждому классу — в §4.
2. **Можно ли ради T5.1 переносить ресурсы с телефона в `main`?** Только точечно — когда ресурс маленький, а перенос убирает настоящий дубль. Копировать ресурсы телефона в приложение часов лишь ради того, чтобы класс скомпилировался, — неправильное решение; вместо этого класс остаётся только на телефоне, за зарегистрированным интерфейсом.
3. **Можно ли в PR по паре менять общий интерфейс?** Да, если поведение не меняется и в описании PR это сказано. Изменение `CustomAlertController.snoozeAlert/ignoreAlert` — хороший пример. Изменение интерфейса, которое меняет поведение, — отдельным PR.
4. **Много маленьких PR или один большой?** Ни то ни другое: пилотный PR на рецепт, затем партии по 5–10 элементов (§8.1).
