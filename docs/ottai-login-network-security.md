# Ottai global and Syai login transport

The supplied `juggluco-trace-20261028-021541.log` shows Ottai web login and
profile lookup succeeding, followed by mobile `/user/accountLogin` returning
`AppDevice_Upgrade_Version`. Syai's web token and login routes return
`NET_SECURITY_PLAINTEXT_ROUTE_FORBIDDEN`, even over HTTPS. These failures precede
sensor access and are independent of BLE pairing.

## Current source and protocol

Syai's public website was inspected on 2026-10-28. The relevant primary sources are:

- [Common client and encrypted transport](https://www.syai.com/_next/static/chunks/pages/_app-caea8a916a3ced2e.js),
  SHA-256 `ca22176c35bf6569623aadc5e3001d08ccce9c881c46b369c81395ebca55a9f6`.
- [Account API routes](https://www.syai.com/_next/static/chunks/156-ea971e674dd5341a.js),
  SHA-256 `fc1b4e885031a67939412eb14b89846b068b464726f15de4c35f5848870cd540`.
- [Sign-in flow and token parsing](https://www.syai.com/_next/static/chunks/9535-e78d0998de788588.js),
  SHA-256 `b58bf9a7e663be65b981f716ec3899df16fe659669a4bbf4c52452b3738122d6`.

The website declares `versionCode=10000000` and uses `webDeviceId` as the cipher
owner, separately from the common account `deviceId`. This compatibility version
is necessary: anonymous probes with the older mobile version can complete key
exchange while their encrypted business parameters remain undecoded. Raising the
version on the old plaintext route alone still returns `AppDevice_Upgrade_Version`.
The secure version and route must change together.

`OttaiRegionalTransport` selects exactly these destinations:

| Caller | Business prefix | Exchange URL |
| --- | --- | --- |
| Syai website | `https://www.syai.com/api/cgm/security/web` | `https://www.syai.com/api/cgm/security/official/server/security/exchangeKey` |
| Syai mobile | `https://api.syai.com/cgm/security/app/server` | Business prefix + `/security/exchangeKey` |
| Ottai global mobile | `https://seas.ottai.com/cgm/security/app/server` | Business prefix + `/security/exchangeKey` |

Every regional mobile request uses this dispatcher, including API-token issuance,
login, profile lookup, account devices, validation, binding and unbinding. Account
identity, authorization and signed common timestamp remain the same. No CN
forwarded-IP headers are added. Ottai website and CN requests retain their existing
transport. There is no retry through a plaintext route.

The codec reuses the authenticated P-256/SHA-256 exchange, HKDF-SHA256 key
derivation, AES-256-GCM query/body encryption, and HMAC-SHA256 request signatures
recovered for the CN 1.63 client in the separate OTA work. The current Syai source
independently confirms the same derivation: salt is `secretId`, HKDF info is
`cipherOwner#expireTime#secretId`, and GCM AAD is `cipherOwner|secretId`.
The website uses a fresh UUID cipher owner and a random 16-byte Base64 request
nonce ID. Mobile requests retain the complete existing install identity and a
numeric nonce ID. Cipher owners and keys are scoped to one HTTP operation and
cleared on completion. Successful responses must authenticate before parsing;
failed responses cannot supply login credentials or sensor materials.

Syai's current web response places its access token at `data.jwtToken.accessToken`.
The login parser supports both nested and legacy direct tokens. The web token
still has to resolve a username and upgrade to a mobile token **with** the
`glucoseSecretKey`; a web-only token cannot count as signed in. Profile lookup
stops after its first successful username. A rejected password is attempted once;
only an explicitly rejected authorization token permits the existing retry
without that authorization.

## Verification

Independent synthetic server tests exercise the production HTTP dispatcher and
decrypt its actual requests. They cover both mobile hosts and Syai web, GET/POST/PUT,
query escaping, unchanged signed timestamps and account identities, nested tokens,
profile lookup count, password rejection, token recovery, business errors, empty
responses and authentication failures. The fixed crypto fixture is generated by
`scripts/ottai/net_security_vectors.py` using public synthetic inputs.

`scripts/ottai/RegionalLoginProbe.kt` exercises the production router and codec
against all three anonymous API-token endpoints. Compile it with `kotlinc`, an
`org.json` JAR, and `OttaiNetSecurity.kt`, `OttaiRegionalTransport.kt`,
`OttaiConstants.kt`, `OttaiBleAuth.kt`, and `OttaiCrypto.kt`; run
`tk.glucodata.drivers.ottai.RegionalLoginProbeKt` from the repository root.
It prints only pass messages and never prints or stores issued tokens or keys.
All three live production-code checks passed on 2026-10-28.

Separate anonymous negative probes with generated nonexistent usernames reached
ordinary `User_InvalidParams` credential validation on both encrypted mobile
hosts and Syai's encrypted email-login endpoint, replacing the trace's route/version
failures. The final retained watch version name was included in these mobile checks.
The focused mobile Ottai/setup suite passed 284 tests with no failures, errors or
skips; Java 21 mobile compilation and Wear Kotlin compilation also passed.
No real account login,
registration, sensor operation or account mutation was performed. Successful
sign-in with the user's account still requires a phone test.

## Typed box serials

The setup text field previously guarded all automatic requests with `looksLikeMac`.
`B4893117F817` passes that 12-hex check, whereas the typed serial `X01269290MMR`
does not. The effect returned immediately, leaving no request or failure message.

Setup now accepts a 12-character alphanumeric box serial as lookup input. While
signed in, typing it starts the vendor's read-only serial-to-MAC request. Only the
resolved, validated hexadecimal MAC enters the existing material/bootstrap flow;
the serial is never treated as a BLE address or persisted sensor identity. A failed
lookup exposes its backend error and can be retried with Search. Cancelling the
effect or changing selection prevents a late lookup from replacing the new input.
The field label includes serial numbers in all 16 supported locales.

The CN 1.63 APK's request builder at `0x8fa9dc` constructs
`/device/getDeviceMacOrSnInfo` with `{mac, colorBoxTailSn}`. Its caller at
`0x12a37a4` uses the POST wrapper at `0x121807c` and reads `data.mac` from the
successful response. When resolving a serial, the optional `mac` is null. The
global 1.33 APK names the corresponding route `/device/getDeviceMacOrSnInfo2`;
regional lookup tries that route, falling back to the current route only on HTTP
404. Authentication, business errors and malformed results do not trigger a
different lookup or provide a usable sensor ID.

Both regional gateways require an account token for these routes: anonymous
checks returned `AuthFailed_TokenNull`. The actual mapping for the supplied serial
has therefore not been verified against a signed-in account. The test mapping to
`B4893117F817` is synthetic. Tests cover direct typed input, existing hex IDs,
encrypted POST dispatch, response validation, route retirement and backend errors.
